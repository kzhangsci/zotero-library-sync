# 0.2.0-beta.15

- 独立验收补修：多文件发布失败完整回滚，撤回原先不存在的新文件；备份与事务记录支持失败恢复。元数据迁移使用相同发布与复验路径。预览绑定实际文件和处置状态，执行时在工作流锁内重新校验。
- 单篇处置记录保存运行中、成功和失败结果；成功后更新诊断、任务列表及下次修复基线，同时保留原任务历史。验收后文件再次变化时要求复查。

- 混合失败批次的安全暂停与恢复：暂停判定改为与收尾原子互斥并置于质检门槛之前（修复 20261118_102159_cd926e 形态的“请求暂停但未生成凭据即受阻”）。暂停凭据升级为 schema 2，逐篇记录 completed/paused/failed：已验收产物仍按冻结哈希严格封存；失败文献的判定原样保留、进入待处理清单，恢复时健康子集只补缺失步骤并完整收尾，失败文献不会被盲目重发模型，也不再把整批卡成受阻。部分阶段失败/单篇 worker 崩溃只隔离该篇。历史遗留的无凭据受阻暂停提供证据核验式恢复：只读核验（控制器/worker 已停、正本与基线哈希、附件身份、Note、逐篇未提交产物清单）→ 显式预览确认 → 新子任务执行，原始记录字节不变、不伪造凭据；证据不足时说明并建议重新预演，不覆盖现有产物。恢复前展示“原任务冻结模型 vs 当前已保存模型”，默认沿用冻结配置，显式选择才用已保存配置（派发后保存配置再变化则拒绝执行并保留记录）；每个恢复子任务记录配置来源。
- 任务页单篇“详情”诊断与安全处置：每行新增详情入口，展示错误码中文释义、失败阶段、文件/单元/字段证据、现有产物与 QC 标记、日志尾部（脱敏截断）、问题台账状态、最近尝试与可用处置；状态刷新不丢失已打开的诊断，支持复制诊断与 Zotero 条目跳转（能力可用时）。原因分类至少区分：可采纳的既有产物、旧版元数据/格式、译文对照/内容、原文/质检/解析、缺正本 PDF 或路径失效（按文件系统实际存在判定；`source_pdf` 质检错误归入元数据不匹配，不当作缺 PDF）、身份/重复/来源冲突、API/鉴权/超时/限流、用户修改、等待/暂停与其他，多原因并存全部保留。处置先预览后确认，确认需一次性令牌，令牌绑定文献字节、已保存模型配置与身份，任一变化须重新预览；伪造/重复/过期令牌一律拒绝。模型类处置（定向修复译文、仅重新翻译中文、重跑质检、显式全新解析）全部在隔离候选目录执行：候选先完整验收，通过才在重新核验源文件/正本/Note/用户修改未变化后逐文件发布（按动作限定发布范围），失败或崩溃不发布任何字节（并对真实目录重新哈希证明），发布后复验失败自动回滚备份；整个处置持有与同步共享的工作流互斥锁。采纳已验收产物不调用模型仅记账；旧版元数据迁移只对齐派生文件可验证字段（不凭当前 PDF 文件名改写旧全文 source_pdf，来源不明须人工核实）；缺 PDF/身份冲突/API 问题/用户修改给明确指引与复查而非假重试；暂缓/排除/撤销可逆。中文原文（MD）与外文（EN）按互斥规则判定采纳条件，后端校验动作可用性而不只靠前端隐藏。

# 0.2.0-beta.14

- 版本一致性改为单一来源并强制校验：`manifest.json` 是唯一版本源，XPI 构建器、面板资源 `?v=`、面板显示版本、面板对话框 URL、诊断版本与 RELEASE.json 全部由它生成或比对；构建在任何漂移上直接拒绝出包。背景：beta.13 曾带着 beta.12 的资源查询串发布，升级后 Gecko 可能按未变的 URI 命中旧缓存脚本——这是已确认的回归风险（可导致空白面板），但并未被证实为当前用户空白面板的唯一或根本原因；在隔离配置的 Zotero 10.0.8 中 beta.13 面板可正常打开。该用户的磁盘配置缺少持久化安装记录而菜单仍在内存中，安装/资源路径问题仍是未决的现场原因，真实环境验证由主会话继续。
- 面板启动生命周期加固：静态标记增加“正在初始化”引导行（脚本完全失败时也可见、含处置提示）；`DOMContentLoaded` 引导改为带阶段标签的受控启动，宿主参数缺失或初始化异常时显示脱敏的阶段与原因，窗口始终可关闭重开；面板就绪采用显式握手（UI 接线完成后、连接/模型工作之前发信号），宿主等待有界超时，超时未就绪时写入脱敏提示并关闭失效窗口、清除引用，重新打开即获得全新面板；面板卸载、组件停机都会清理监视计时器与监听；断网、bridge 缺失、CLI 未登录均不再阻塞完整设置界面。
- GLM 模型目录即时可用：识别到官方默认端点（通用 API / Coding Plan / DeepSeek / 同济）时立即显示带来源标记的内置官方文档候选（离线快照、明示非账号清单），再异步联网刷新，刷新失败保留候选、手填模型与文献选择；自定义地址不种官方候选。QC/ZH 并行、目录身份与迟到响应丢弃等既有保护保持。
- ZCode 登录（本机 CLI 直连）诚实停用：先前实现把该服务商的调用接到 `glm_client` 的私有 home 方案上，而那会整体复制本机 `~/.zcode/v2`（含凭据）——本版彻底移除该路径，也不再宣称"无需 Key 的 ZCode 登录"。安装版 CLI 无头模式没有按模型调用参数（`--help` 已核），其 app-server 虽有 `session/setModel`、`session/setThoughtLevel` 等按会话模型接口，但本插件未实现、未验证该协议，因此两个订阅（Coding / Start Plan）一律如实报告“不可用”并使用固定原因码：不复制本机凭据、不启动无头进程、不自建私有 OAuth、也不改走任何计费服务商。Coding 路由的事实核查同时收紧：只有本机 CLI 的 bigmodel 服务商确为官方登录托管的 Coding Plan 配置（anthropic 协议、官方端点、`apiKeyRequired` 且无内联 Key、无自定义请求头）才报告 `login_route_unavailable`（我们未实现安全直连）；端点被改指任意地址或只是保存的 API-Key 配置时报告 `provider_config_unsupported`，绝不凭服务商名宣称 Coding Plan；CLI 可执行文件缺失亦有独立原因码。App 侧 Start 服务商的"enabled"标志与其自由文本停用原因一律不读、不抄（模型 ID 仅作显示性事实单独上报）。已保存的 zcode 配置仍可解析、显示（GET /v1/config 不因此失败），测试/列表/保存按订阅明确禁用并给出迁移指引（改选 API Key 服务商）；连接旧版后台（beta.13，无 `zcode-plans-v1` 能力）时同样停用 ZCode 登录请求，并提示升级服务或迁移至 API Key 配置。最终验收补口：已保存的必需 zcode 角色（登录标志为真也不例外）在面板就绪度/预演预检/开始确认三处一律失败关闭——按已保存配置判定而非未保存的下拉草稿，翻译关闭时未用到的 zh 角色不阻塞 QC 路径；新版后台在 make_plan/工作/抽取之前以固定原因码 `zcode_route_unavailable` 拒绝必需 zcode 角色（登录存在性仅为显示事实，不再充当凭据），旧版后台上的已保存 zcode 配置也不再发出任何预演/开始请求。缓存身份继续包含订阅与生效档位；档位/模型草稿字段仍可编辑保存以便迁移。
- 默认推理参数按用户偏好统一（2026-11-17）：所有受支持服务商/模型的新建模板与“恢复插件初始参数”默认 thinking 开启、reasoning_effort=high（GLM-5.3 官方默认为 max、DeepSeek 官方默认为 high、ZCode CLI 配置默认为 max；插件默认是用户偏好，与官方默认、最高档三者明确区分并在说明中标注）。同济不发送 thinking，思考由 effort 表达，新模板同样默认 high（两个已核实校内模型档位均含 high）。选择已知模型改为填写推荐默认参数（thinking 开启 + effort high）；模型文档档位无 high 时在文档支持档位内回退（如 [low,medium] → medium）并说明，无任何思考档位时不自动填写；档位仍出现未知值时不推荐。“按该模型最高值填写”按钮保留（显式填 max），全部候选/手填选项不移除。已保存配置（含 default/max/自定义档位）原样保留、绝不静默迁移；文档元数据继续区分服务端默认档与最高档。开发用 ZCode CLI 代理本身仍保持 GLM-5.3 max 档不变。
- 保持 beta.11 翻译修复/报告三个月清理与 beta.12 原始附件/标题/补充材料行为不变；本轮离线测试与打包验证由主会话执行记录。
